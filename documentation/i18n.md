# Internationalization (i18n)

## How locale works

The plugin does **not** pick a language itself. It follows the **WordPress site locale** (`Settings → General → Site Language`).

1. Text domain: `wc-payment-gateway-boilerplate`
2. Domain path: `/languages`
3. `load_plugin_textdomain()` runs on boot (`Plugin::load_textdomain()`)
4. PHP strings use `__()` / `esc_html__()` / etc.
5. Blocks JS uses `@wordpress/i18n` (`wp.i18n`) + `wp_set_script_translations()` when available

## Template

- `languages/wc-payment-gateway-boilerplate.pot` — translation template for v1.0

Generate / refresh with your preferred toolchain (WP-CLI `i18n make-pot`, Poedit, etc.):

```bash
# Example with WP-CLI (inside an environment that has wp-cli + the plugin path)
wp i18n make-pot . languages/wc-payment-gateway-boilerplate.pot --domain=wc-payment-gateway-boilerplate
```

## Adding a language

1. Copy the `.pot` to e.g. `languages/wc-payment-gateway-boilerplate-es_ES.po`
2. Translate
3. Compile to `.mo` (or ship `.l10n.php` on modern WP)
4. Switch the site language to `es_ES` and verify checkout/admin strings

## What to translate

- Gateway titles/descriptions (defaults)
- Admin labels
- Customer-facing errors

## What not to put through gettext

- API keys / secrets
- Provider payment ids
- Raw log payloads (and never log card data)

## Multilingual plugins (WPML / Polylang)

Out of scope for v1.0 code. The plugin is **gettext-ready**; those tools can translate strings/settings if needed. See future notes if a client requires a dedicated guide.

## Rename warning

When you fork the boilerplate, change the text domain **once** and keep it stable. Changing it later breaks existing translations.
